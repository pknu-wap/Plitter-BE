# 캐릭터 생성 다양화 구현 계획서

- 프로젝트: Plitter-BE
- 작성일: 2026-11-23
- 상태: 설계안. 이 문서 작성으로 애플리케이션 코드나 운영 DB를 변경하지 않는다.
- 목표: 음악 취향을 반영하면서 이미지·이름·태그가 서로 어울리고, 재생성마다 다른 콘셉트를 제공한다.

## 1. 사용자 표현 방향

### 1.1 확정할 기준

| 항목 | 적용 방향 |
| --- | --- |
| 이름 구조 | 형용사 또는 형용사구 + 공백 + `스타` |
| 이름 분위기 | 짧고 자연스러운 일상어에 장난기를 더한다. |
| 수식어 | `괜히`, `은근`, `유난히`, `대놓고`, `쓸데없이` 등을 허용한다. |
| 지양할 표현 | `사색적인`처럼 어렵거나 추상적인 표현, 이름 끝의 `별` |
| 태그 분위기 | `새벽감성`, `과몰입`, `내적댄스`처럼 음악을 듣는 자기 모습이 떠오르는 표현 |
| 이름과 태그 관계 | 이름은 성격을, 태그는 감정·상황·음악을 즐기는 모습을 표현한다. |
| 공통 콘셉트 | 이미지 지시와 이름·태그를 하나의 선택 결과에서 만든다. |

### 1.2 초기 문구 후보

아래 문구는 후보 사전의 출발점이다. 전체 후보는 구현 시 어색함·중복·음악 분위기와의 적합성을 검수한다.

| 이름 후보 | 태그 예시 | 적용할 느낌 |
| --- | --- | --- |
| 괜히 센치한 스타 | `#새벽감성` `#감성충전` `#무한반복` | 조용하고 감성적인 음악 |
| 유난히 말랑한 스타 | `#이불속콘서트` `#힐링중` `#새벽감성` | 부드럽고 편안한 음악 |
| 은근 뻔뻔한 스타 | `#내적댄스` `#은근흥부자` `#못멈춰` | 장난스럽게 리듬을 즐기는 느낌 |
| 대놓고 힙한 스타 | `#이어폰필수` `#내적댄스` `#느좋` | 자신감 있고 개성 있는 느낌 |
| 쓸데없이 비장한 스타 | `#플리과몰입` `#볼륨주의` `#과몰입중` | 강하고 몰입감 있는 음악 |
| 묘하게 잔망스러운 스타 | `#혼자페스티벌` `#텐션업` `#둠칫둠칫` | 밝고 신나는 음악 |

이름은 공백 포함 18자 이내, 태그는 `#`를 포함해 각 12자 이내로 제안한다. 태그는 서로 다른 3개를 반환한다. 장르 태그를 반드시 포함하지 않아도 된다. `새벽감성`은 창작된 분위기 표현이며 실제 재생 시간, 생활 습관, 성격을 측정한 결과로 설명하지 않는다.

## 2. 현재 구조와 개선할 문제

| 현재 동작 | 문제 | 변경 방향 |
| --- | --- | --- |
| 분위기 4종 분류 | 많은 입력이 `balanced`로 합쳐진다. | 9개 분위기와 정보 부족 상태로 구분한다. |
| 분위기별 지시문 4개 순환 | 다른 사용자 요청과 서버 재시작이 선택 순서에 영향을 준다. | 요청별 seed와 후보 조합으로 선택한다. |
| 이미지와 메타데이터가 별도로 분위기 계산 | 동일 입력에서 이미지와 이름·태그가 달라질 수 있다. | 공통 음악 프로필과 콘셉트를 사용한다. |
| 장르 별칭과 지원 목록 불일치 | `hip hop`, `k pop`, `electronic` 등이 충분히 반영되지 않는다. | 집계 전에 표준화하고 장르별 후보를 확대한다. |
| 이름이 장르와 분위기에 고정 | 같은 취향의 이름이 반복된다. | 검수한 이름 후보를 콘셉트에 맞춰 선택한다. |
| 조회할 때 이름·태그 재계산 | 규칙 변경 시 기존 캐릭터의 설명이 달라질 수 있다. | 신규 결과의 최종 이름·태그를 저장한다. |
| 특징 없는 평균을 0으로 기록 | 정보 부족이 낮은 에너지·낮은 밝기로 해석될 수 있다. | 누락값과 실제 0을 구분한다. |

현재 energy·valence는 Last.fm 태그에서 추정한 값이다. 오디오에서 직접 측정한 값처럼 설명하지 않는다. 사용자 제공 운영 DB 조회 결과에는 `LASTFM_TAG` 108행과 `LASTFM_EMPTY` 5행이 있었으며, 이 집계만으로 수치 분포나 추천곡 전체의 분석 누락 여부까지 확인된 것은 아니다.

## 3. 구현 범위

### 3.1 첫 버전에서 구현

- 음악 특징 집계와 장르 정규화.
- 공통 분위기 분류와 정보 부족 처리.
- 콘셉트 후보 사전, 가중치 선택, 최근 조합 중복 회피.
- 콘셉트 기반 프롬프트·이름·태그 생성.
- 선택 결과와 메타데이터 저장, 기존 캐릭터 조회 호환.
- 자동 테스트와 대표 이미지 품질 검토.

이름·태그는 후보 사전과 규칙으로 생성한다. 외부 이미지 편집 호출은 기존 흐름을 사용한다. 생성 API의 추천 5건 조건과 응답 필드는 유지한다.

### 3.2 별도 작업으로 관리

| 작업 | 관계 |
| --- | --- |
| Last.fm 실패 시 기존 성공값 보존·재시도 | 음악 분석 데이터 품질 개선 작업으로 추적한다. |
| HTTP 재요청의 멱등성·생성 작업 상태 관리 | seed만으로 해결되지 않으므로 별도 설계한다. |
| S3 업로드 후 DB 저장 실패 시 보상 처리 | 생성 안정성 작업으로 추적한다. |
| 반투명 선 후처리 개선 | 이미지 검토 시 영향을 분리하고, 필요한 수정은 별도 작업으로 관리한다. |
| LLM을 통한 문구 생성 | 후보 사전 방식의 반복률과 품질을 확인한 뒤 검토한다. |

## 4. 변경 후 생성 흐름

1. 소유자와 추천 5건 조건을 확인한다.
2. 저장된 곡 특징을 읽고, 서로 다른 곡 기준으로 음악 프로필을 만든다.
3. 공통 분류기로 분위기와 장르를 결정한다.
4. 생성 요청의 seed와 최근 생성 이력을 바탕으로 콘셉트를 선택한다.
5. 같은 콘셉트에서 이미지 편집 지시와 최종 이름·태그를 만든다.
6. 기본 캐릭터 이미지와 편집 지시로 이미지를 생성하고 S3에 저장한다.
7. 별도 DB 트랜잭션에서 기존 생성 정보와 신규 콘셉트·메타데이터를 함께 저장한다.
8. 저장된 이름·태그를 생성 응답에 포함한다.
9. 상세 조회와 다운로드 응답도 저장된 이름·태그를 사용한다.

외부 이미지 호출과 S3 업로드는 현재처럼 캐릭터 저장 트랜잭션 밖에서 수행한다. DB 저장을 재시도할 때 콘셉트나 이름을 다시 선택하지 않는다.

## 5. 음악 프로필 규칙

### 5.1 집계 단위

- 추천 횟수는 생성 자격을 판단하는 데 사용한다.
- 음악 특징은 서로 다른 `track_id`마다 한 번씩 동일 가중치로 집계한다. 이는 기존 추천 건별 가중에서 의도적으로 변경하는 정책이다.
- energy·valence는 각각 값이 존재하고 0~1 범위인 표본으로 평균을 계산한다. 실제 `0`은 유효한 값이다.
- 범위를 벗어난 값은 해당 축의 표본에서 제외하고 진단용 개수를 기록한다.
- 표본이 없으면 평균은 `null`, 표본 수는 0으로 기록한다.
- `analyzedTrackCount`는 특징 행 존재 여부와 구분해 정의하고, 실제 유효값을 가진 곡 수를 별도로 기록한다.
- 분석 비율, 축별 표본 수, 평균 confidence를 기록한다. 첫 버전에서는 검증되지 않은 confidence 임계값으로 곡을 제외하지 않는다.

### 5.2 분위기 분류

각 축에 서로 다른 유효 곡 2개 이상이 있어야 9개 분위기 분류를 적용한다. 한 축이라도 부족하면 `UNKNOWN`으로 처리하며 확인 가능한 장르 정보는 유지한다.

| 축 | LOW | MID | HIGH |
| --- | --- | --- | --- |
| energy | `0 <= x < 0.40` | `0.40 <= x < 0.65` | `0.65 <= x <= 1` |
| valence | `0 <= x < 0.40` | `0.40 <= x < 0.60` | `0.60 <= x <= 1` |

| energy / valence | LOW | MID | HIGH |
| --- | --- | --- | --- |
| LOW | 새벽감성 | 느긋한 느낌 | 말랑한 느낌 |
| MID | 센치한 느낌 | 느좋 | 기분업 |
| HIGH | 볼륨업 | 내적댄스 | 흥부자 |

위 표는 후보 선택용 콘셉트 그룹이다. 그룹명이 그대로 최종 이름이 되는 것은 아니다. 내부 값은 `LOW_LOW` 같은 안정적인 enum 코드로 관리한다. 경계값은 첫 버전의 설정값이며 실제 분포와 결과 검토 후 규칙 버전을 올려 조정한다.

정보 부족 시 감정·에너지를 단정하지 않는 기본 후보를 사용한다. 예: `느낌 있는 스타`, `#음악친구 #플리탐험 #이어폰필수`.

### 5.3 장르 정규화

| 입력 예시 | 생성용 장르 코드 |
| --- | --- |
| `k-pop`, `kpop`, `k pop` | `K_POP` |
| `hip hop`, `hip-hop`, `hiphop`, `rap` | `HIP_HOP` |
| `r&b`, `rnb` | `RNB` |
| `electronic`, `edm`, `dance` | `ELECTRONIC_DANCE` |
| `pop`, `rock`, `jazz`, `ballad` | 각각의 장르 코드 |
| `indie`, `classical`, `acoustic`, `folk`, `metal` | 각각의 장르 코드 |
| 빈 값, `balanced` | `UNKNOWN` |
| 그 밖의 태그 | 원문을 보존하고 생성용 코드는 `OTHER` |

집계 전에 별칭을 정규화해 분포를 합산한다. 대표 장르 동률은 정렬된 장르 코드 순으로 결정해 조회 순서에 영향을 받지 않게 한다. 대표 장르를 기본 입력으로 사용하고, 보조 장르와 곡 간 에너지 차이를 활용하는 확장은 후속 단계로 둔다.

## 6. 콘셉트 후보 사전과 선택

후보 사전은 `src/main/resources/character/character-concepts-v2.json`으로 관리하는 방안을 제안한다. 기본 규칙은 명시적인 타입으로 읽고 시작 시 검증한다.

| 요소 | 초기 구성 목표 | 선택 기준 |
| --- | --- | --- |
| 표정 | 분위기별 3개 이상 | 분위기와 어울리는 표정 |
| 포즈 | 에너지 단계별 4개 이상 | 동작 크기와 리듬감 |
| 소품 | 지원 장르별 2개 이상 | 장르 적합성·크기 제한 |
| 주변 표시 | 분위기별 3개 이상 | 음표·움직임 선·반짝임·표시 없음 |
| 이름 | 분위기별 6개 이상, 기본 후보 별도 | 형용사구·길이·말투 검수 |
| 태그 | 분위기별 사용 가능한 후보 8개 이상 | 감정·상황·행동 범주를 함께 확보 |

후보에는 `id`, 적용 가능한 분위기·장르, 기본 가중치, 금지 조합을 정의한다. 태그에는 유사 의미를 묶는 그룹을 추가해 `과몰입중`과 `플리과몰입`만으로 슬롯을 채우지 않게 한다.

선택 순서는 다음과 같다.

1. 프로필과 호환되는 후보를 추린다.
2. 소품 수·실루엣·얼굴 가림 등 공통 제약을 적용한다.
3. 최근 3개와 같은 표정·포즈·소품·주변 표시 조합을 우선 제외한다.
4. 정렬된 후보 목록에서 요청별 seed를 사용해 가중치 선택한다.
5. 최근 사용 이름도 대안이 있으면 우선 제외하고, 선택한 콘셉트와 어울리는 이름·태그를 확정한다.
6. 후보가 소진되면 가장 오래된 중복부터 허용한다. 결과와 선택 이유를 저장한다.

최근 3개는 해당 플레이리스트의 성공적으로 저장된 캐릭터를 기준으로 한다. 구조화된 콘셉트가 없는 기존 기록은 조합 비교에서 제외한다. 동시에 실행되는 요청 사이의 중복 회피는 최선 노력으로 처리하며 유일성을 보장하지 않는다.

seed 재현 조건은 동일한 프로필·규칙·후보 사전·이력 입력이다. 저장 후 정확한 콘셉트 복원은 선택된 구성 요소를 기준으로 한다. 같은 seed가 이미지 API의 픽셀 단위 재현을 보장하는 것은 아니다. 별개의 POST 재요청은 새 요청으로 취급한다.

## 7. 이름·태그·프롬프트 생성 규칙

### 7.1 이름

- 검수된 전체 이름 후보를 우선 사용한다. 수식어와 형용사를 무제한으로 연결하지 않는다.
- `형용사구 + 스타` 형식, 공백 포함 18자 이내를 검사한다.
- `별`, `친구`, `요정` 등을 이름의 마지막 단어로 사용하지 않는다.
- 어려운 표현, 모욕적인 표현, 과도한 신조어, 같은 의미의 반복을 제외한다.
- 소품과 무관한 캐릭터나 상황을 이름에서 강하게 단정하지 않는다.

### 7.2 태그

- 서로 다른 태그 3개를 반환한다. 각 태그는 `#`를 포함해 12자 이내로 제한하고 공백을 포함하지 않는다.
- 감정·상황·행동 중 가능한 서로 다른 범주를 조합한다. 장르는 선택 가능한 별도 범주다.
- 같은 콘셉트에서 어울리는 표현을 사용하고, 유사 의미 태그만 반복하지 않는다.
- 장르·분위기가 확인되지 않으면 성격이나 감정을 단정하는 태그를 사용하지 않는다.
- 이름과 태그에 쓰는 재미있는 상황 표현은 창작된 캐릭터 설정으로 취급한다.

### 7.3 프롬프트

프롬프트는 다음 순서로 작성한다.

1. 공통 정체성: 다섯 꼭짓점 별 몸체, 얇고 불규칙한 흑백 낙서 선, 전신 캐릭터 1개, 투명 배경.
2. 음악 맥락: 정규화된 대표 장르와 공통 분위기.
3. 선택된 콘셉트: 표정·포즈·주요 소품·주변 표시를 구체적으로 명시.
4. 금지 조건: 얼굴 가림, 실루엣 대체, 주요 소품 2개 이상, 복잡한 의상, 과도한 색·음영.

재미있는 한국어 이름과 태그는 이미지에 글자로 그리도록 지시하지 않는다. 현재 이미지 클라이언트가 추가하는 보존 규칙도 함께 검토해 같은 제약을 일관되게 적용한다.

## 9. 데이터 저장과 호환

`characters`에 nullable JSONB 컬럼 두 개를 추가한다.

| 컬럼 | 내용 |
| --- | --- |
| `generation_spec_json` | 스키마 버전, seed, 규칙·프롬프트·후보 사전 버전, 음악 프로필, 선택된 요소·이름·태그 ID, 선택 시 적용한 중복 회피 정보 |
| `result_metadata_json` | 최종 `characterName`, `tags` |

기존 `feature_summary_json`은 집계 입력을, `prompt_text`는 실제 편집 지시 본문을 계속 저장한다. 전송 단계에서 추가되는 공통 규칙은 해당 코드·프롬프트 버전과 함께 추적한다.

신규 생성의 JSON 예시:

```json
{
  "schemaVersion": 2,
  "ruleVersion": "v2",
  "promptVersion": "v2",
  "catalogVersion": "v2",
  "seed": 842731,
  "moodId": "LOW_LOW",
  "genreId": "BALLAD",
  "expressionId": "soft_smile",
  "poseId": "gentle_sway",
  "propId": "small_record",
  "marksId": "two_notes",
  "nameId": "casually_sentimental",
  "tagIds": ["late_night_mood", "emotional_recharge", "on_repeat"]
}
```

이 예시는 핵심 필드만 표현한다. 실제 저장 타입에는 집계 시 사용한 음악 프로필과 선택 이력 정보를 포함한다. seed는 예시값이며 실제 생성에서는 요청마다 만든다.

```json
{
  "characterName": "괜히 센치한 스타",
  "tags": ["#새벽감성", "#감성충전", "#무한반복"]
}
```

조회 우선순위는 다음과 같다.

1. 유효한 저장 메타데이터가 있으면 그대로 반환한다.
2. 기존 레코드처럼 새 컬럼이 없으면 기존 생성 규칙으로 계산한다.
3. V2 레코드에 메타데이터가 누락되거나 손상됐으면 장애로 기록하고, 버전이 맞는 콘셉트 ID로 복구 가능한 경우에만 복구한다. 조용히 새 이름을 다시 선택하지 않는다.

생성·상세·다운로드 응답의 필드와 태그 개수는 유지한다. 기존 데이터를 일괄 재생성하거나 덮어쓰는 작업은 포함하지 않는다.

## 10. 구현 순서와 산출물

| 단계 | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| 1 | 공통 프로필·장르·누락값 처리 | 타입·집계·분류기와 경계값 테스트 |
| 2 | 후보 사전·콘셉트 선택기 | 이름·태그 후보 검수, 제약 검사, seed·이력 테스트 |
| 3 | 프롬프트·메타데이터 연결 | 이미지·이름·태그가 하나의 콘셉트를 사용 |
| 4 | DB 저장·기존 조회 호환 | 스키마 변경 SQL, ORM 저장·재조회, 과거 레코드 테스트 |
| 5 | 다양성·대표 이미지 검토 | 고정 입력별 반복률 보고와 이미지 검토 결과 |
| 6 | 적용 준비 | 설정 기본값, 전환·복구 절차, API 회귀 확인 |

배포 단위는 1~3단계의 생성 규칙, 4단계의 저장·조회 연동, 5~6단계의 검증·적용 준비로 나눌 수 있다. 운영 DB 접속이나 이미지 API 사용 가능 여부에 따라 검증 일정을 조정하며, 이 계획서에는 확인되지 않은 완료 일정을 기재하지 않는다.

## 11. 검증 기준

### 11.1 필수 자동 테스트

| 검증 | 통과 기준 |
| --- | --- |
| 구간 경계 | `0`, `0.40`, `0.60`, `0.65`, `1`에서 정의한 구간을 반환 |
| 정보 부족 | 표본 0·1개, `null`, 잘못된 범위에서 실제 낮은 값으로 오인하지 않음 |
| 중복 추천 | 동일 곡 반복 추천이 특징 표본 수를 늘리지 않음 |
| 장르 별칭 | 공백·하이픈 별칭이 같은 생성용 장르와 분포로 집계됨 |
| 분류 일관성 | `energy=0.48`, `valence=0.20` 등에서 이미지·이름·태그가 동일 프로필을 사용 |
| 콘셉트 재현 | 동일 프로필·seed·규칙·사전·이력 입력에서 동일 선택 |
| 후보 유효성 | 지원하는 분위기·장르 조합마다 유효한 시각 조합 최소 24개 |
| 다양성 | 고정 프로필·고정 이력에서 서로 다른 고정 seed 200개로 생성 시 시각 조합 16개 이상 |
| 최근 중복 회피 | 대안이 있는 순차 생성에서 최근 3개와 같은 시각 조합을 선택하지 않음 |
| 문구 형식 | 모든 이름의 끝이 `스타`, 길이 제한 충족, 서로 다른 태그 3개 |
| 저장·재조회 | 생성 응답과 상세·다운로드의 이름·태그가 동일 |
| 과거 데이터 | 새 컬럼이 없는 레코드를 기존 방식으로 조회 가능 |
| 저장 재시도 | 같은 이미지·콘셉트·이름·태그를 재사용하며 다시 선택하지 않음 |

다양성 수치는 첫 버전의 구현 목표다. 특정 이름·태그·소품으로 선택이 쏠리는지도 고정 seed 집계 결과로 보고한다. 조합 개수로 이미지의 시각적 차이까지 보장했다고 판단하지 않는다.

### 11.2 대표 이미지 검토

첫 검토는 9개 분위기마다 같은 프로필에서 서로 다른 콘셉트 2개씩 총 18개와 `UNKNOWN` 2개, 총 20개를 기준으로 제안한다. 장르는 서로 다른 소품군이 포함되도록 배치한다.

- 별 실루엣과 기본 손그림 정체성이 유지되는가.
- 선택한 표정·포즈·소품 차이가 눈에 보이는가.
- 주요 소품은 1개이며 얼굴과 몸체를 가리지 않는가.
- 투명 배경·흑백 낙서체·전신 1개 조건을 지키는가.
- 이름·태그가 계획한 콘셉트와 어울리는가.
- 이미지 원본과 후처리 결과를 비교했을 때 얇은 선이 과도하게 진해지지 않는가.

이미지 생성 검토는 외부 호출 비용이 발생하는 실제 검증 단계다. 이 문서 작성 과정에서는 이미지를 생성하지 않는다. 실패 사례는 콘셉트 ID와 버전을 기록해 후보 사전·프롬프트·후처리 중 원인을 구분한다.

## 12. 적용과 복구 절차

1. 기존 이름·태그 조회 결과와 신규 컬럼 유무를 확인한다.
2. 두 nullable 컬럼을 추가하는 스키마 변경을 준비하고 개발·검증 DB에서 확인한다.
3. 저장 메타데이터 우선 조회와 기존 레코드 호환 코드를 먼저 적용한다.
4. 생성 규칙 선택 설정을 도입해 초기에는 V1 생성으로 시작한다.
5. 자동 테스트와 대표 이미지 검토 후 V2 생성을 전환한다.
6. 전환 뒤 분위기별 생성 수, `UNKNOWN` 비율, 조합·이름 반복률, 실패 단계를 관찰한다.
7. 문제가 발생하면 새 생성만 V1로 되돌린다. 이미 저장한 V2 메타데이터를 읽는 기능은 유지한다.

현재 코드에는 `ddl-auto=update`가 설정돼 있지만, 운영 스키마 적용 여부를 자동 갱신에만 의존하지 않는다. 전체 애플리케이션을 과거 버전으로 되돌릴 경우 V2 메타데이터 조회 동작이 달라질 수 있으므로, 단순 코드 롤백과 생성 규칙 전환을 구분한다.
